## NEW Critical Findings (not present in v1)

### 🔴 ERR-0 — ALL pages return HTTP 500 (site-wide server error)

**Confirmed by:** `curl -s -I https://anti-dv.vercel.app/` → `HTTP/2 500`

Tested routes and their HTTP status:

| Route | HTTP Status |
|-------|------------|
| `/` | 500 |
| `/resources` | 500 |
| `/feedback` | 500 |
| `/stories` | 500 |
| `/psych-resources` | 500 |
| `/docs-toolkit` | 500 |
| `/robots.txt` | 404 |
| `/sitemap.xml` | 404 |

The Next.js App Router RSC layer is throwing an unhandled server component error. The RSC error payload contains the digest `3116509932`. The page content **does still render in JavaScript-enabled browsers** via client-side hydration, but the HTTP status code sent to crawlers is 500.

**Why this matters for SEO:**

- Googlebot and all major crawlers respect HTTP status codes. A persistent 500 response causes Google to mark the page as temporarily unavailable and eventually remove it from the index.
- This error is not related to our pending code changes (which haven't been deployed — confirmed by robots.txt still returning 404). It's a regression in the existing deployed build.

**Immediate fix required:** Identify the failing server component and resolve it before any other SEO work takes effect.

---

### 🔴 ERR-1 — `<meta name="robots" content="noindex">` injected site-wide by error handling

**Confirmed by:** `curl -s -L https://anti-dv.vercel.app/ | grep 'meta name="robots"'`

```html
<meta name="robots" content="noindex"/>
```

When Next.js App Router encounters an unhandled error in a Server Component, it wraps the entire page in `<html id="__next_error__">` and automatically injects `<meta name="robots" content="noindex">`. This is Next.js's built-in safety mechanism to prevent error pages from being indexed.

**Effect:** Googlebot is currently receiving an explicit `noindex` directive on every single page of the site. Any previously indexed pages will be de-indexed in the next crawl cycle. The entire site is effectively invisible to search engines right now.

**Root RSC error payload (from source):**

```
2:E{"digest":"3116509932"}
```

```
1b:{"metadata":[],"error":null,"digest":"$undefined"}
```

The metadata slot resolves to an empty array — confirming that no `<title>`, `<meta name="description">`, or any other head metadata is being served.

---

### 🔴 ERR-2 — HTML `<head>` is empty (no title, no description, no any metadata)

**Confirmed by:** full HTML source inspection

The actual `<head>` served in the HTTP response:

```html
<head>
  <meta charSet="utf-8"/>
  <meta name="viewport" content="width=device-width, initial-scale=1"/>
  <meta name="robots" content="noindex"/>
  <!-- + script preloads -->
</head>
```

No `<title>`. No `<meta name="description">`. No Open Graph tags. No canonical. No JSON-LD. The `AsyncMetadataOutlet` in the RSC payload resolves with `{"metadata":[],"error":null}` — empty metadata array.

This is worse than the v1 state (where at least a fallback title from the browser tab was possible). The error page renders with zero page identity.
